分工是硬约束：
- zcode：只做不依赖视觉判断的性能归因、输入响应、加载/取消/失败恢复、资源寿命、算法等价和状态/轨迹数值验证。禁止用截图转文字模型代替直接看图，禁止接“看起来不真实/不自然”的主观修复卡；它可以为Anti捕获图片但不能替Anti写视觉PASS。卡顿必须用可复现时序/trace/帧间隔/资源数据衡量，平均FPS不是唯一指标，不能以降分辨率/丢LOD/削掉图层冒充性能优化。
- Anti：直接观察固定候选的正常UI/连续过程，先用小机位集复核当前成果，再做一站或一个对象的局部视觉原型。它应记录自己实际看到的事实，保持源码可解释，给前后同机位对照。不能动世界尺度/时间/相机语义来掩盖视觉问题，不能以看起来对了替代数值正确性。
- 你：明确共享接口和不变量、评估架构争议、做代码可支持的技术复核。无工具/无画面就写缺口，不伪装成本地执行或视觉批准。用户做最终审美选择。

并行方式：两人各用一个独立worktree、短任务分支、独立dist/依赖缓存/端口/浏览器profile/证据目录。共享一个冻结基线，无需实时拉取对方WIP。按具体模块和语义划分任务，不能仅按“前端/后端”分配。SolarEngine、CameraController、contracts、公共地形/资源管理、App、来源清单、锁文件等热点每轮只有一位写入者；需要对方接入时提交小的接口请求或独立补丁，受影响子步骤等接入，其余任务继续。先写稳定契约，允许对固定fixture开发；fixture通过不等于真实集成完成。

请交付以下内容：
1. **一张两轨任务表**：每人1个主卡+1个明确允许的低耦合后备卡即可。每卡给目标、依赖、写文件范围/禁止范围、输入/输出、何时能开始、停止条件、风险与回退。任务范围应能形成小提交，不用虚构完成天数或收益。
2. **依赖关系**：标清哪些现在就可同时做，哪些只在最终集成时汇合；若存在硬依赖，提出可先完成的测量/测试/素材核验/独立原型部分，不让整条线停工。历史两个待视觉验收名额不能静默清零；Anti先复核积压，新的视觉生产接入遵守原闸门，原型/修复可继续。
3. **明确验收**：zcode给前后三次同条件有效配对、波动、最长任务/输入响应/首次就绪、必要资源/取消反例；Anti给少量固定时刻/光照/机位的实图或连续视频和直接观察结论。只有受影响路径需重测，不要求每卡重跑全部天体。视觉反馈不得成为zcode开始工程工作的前置条件；进入可玩集成版时才必须补齐适用复核。
4. **两段完整启动prompt**：一段给zcode，一段给Anti，能单独复制使用，明确目录、起始SHA、任务ID、读取文件、第一步、不得做的事、输出报告位置、后续卡和升级条件。不要要求两者先读全部历史聊天。
5. **一次集成检查点**：各自冻结提交后，在单独候选目录组合，记录base/两个head/最终candidate，检查性能×视觉联合作用。串行合并和共享GPU测量；其他编码与CPU工作继续。zcode可担任协调/集成人但不能自授视觉批准；Anti自写材质不能自授独立视觉批准。缺独立复核保留候选，不自动合main/部署，也不因此阻止独立支持任务。
