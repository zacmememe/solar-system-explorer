## 分工与当前运行模式

已有功能的体验维护与 zcode/Anti 执行边界见 [体验底线](experience-foundations.md)。它补充具体反例与验收路径，不替代下文的独立批准规则。用户明确授权 Codex 接手专项修复时，按唯一队列记录实际作者；不要仍把暂停中的 zcode 写作活跃作者。

zcode 主工程/数据/验证，Anti 主视觉/体验工程与实际浏览器复核；职责按任务语义划分，不按前后端或固定天体数量分家。Codex 只做少数关键契约判断与难题，Pro 做阶段深审，Zac 在大体验节点决策。角色分工是本项目起始假设，两轮切片后依据返工和逃逸问题调整。

**Anti 暂不可用期间**：zcode 是唯一业务作者，持续完成当前已批准范围、自动验证、UI 操作和证据准备。能看图则如实自检；不能可靠看图则标 NOT_OBSERVED。无论自检强弱，都不能自授独立批准。当前轮自然结束才切换本流程，不倒推撤销已有提交。

## 单一任务状态与连续工作

本机唯一动态队列：`D:\Game Zac\Personal Projects\太阳系漫游\review-exports\coordination\queue.md`。从任意 worktree 开工都读取该绝对路径；只由指定值班会话写入/分配，其他会话提交短报告。最初作者会话可以维护自己的任务记录，但维护队列不等于有权独立批准自己的代码。

队列包含：task ID、当前状态、风险、owner session、目录/分支/base、依赖、冻结 head/candidate、技术/数据/视觉/架构验收状态、证据链接、下一步。变更提交与审查必须用完整 SHA；正在修改的工作区只记录为 WIP，不能称冻结版本。

状态按 `READY → IMPLEMENTING → READY_FOR_REVIEW → APPROVED → INTEGRATING → VERIFIED → MERGED`；问题回 `CHANGES_REQUESTED`，条件缺失记 `BLOCKED`。行为、视觉、体验接受分列；MERGED 不意味着用户接受。

完成任务可直接领取自己预分配且依赖满足的下一 READY 卡，不每次向用户请示。没有就绪任务时，优先补当前证据、反例、来源/数据验证；不自行扩到全部32天体。等待时留下检查点并结束本次运行，不空轮询消耗额度。

## 风险与批准

| 级别 | 实际语义 | 进入稳定 main 前所需 |
| --- | --- | --- |
| L | 无语义文档/机械整理，排除来源许可、测试政策、权限与契约 | 相应差异检查/自动验证，独立短会话核对，可同工具 |
| N | 已批准契约内的局部实现/数据/材质/修复 | 自动验证、独立技术和适用的数据/视觉评审，至少一次跨工具复核 |
| H | 时间/单位/参考系、相机权属、高程 datum、存档格式、全局资源生命周期、验收政策 | 预先的不变量/迁移、候选实测、对应技术/视觉/数据审查；Codex 或适配范围内的 Pro 一次定向架构复核 |
| X | 产品真值/路线取舍、费用、部署、权限、可见性、历史重写 | 对应具体用户授权，不能用普通开发授权代替 |

按 diff 的语义判断，不按碰了哪个文件机械升级。作者可以建议风险，不能自行降低。共享政策由本次获授权方案作为初始基线；后续改阈值或批准规则单独审，不用同一补丁降低后的门槛批准该补丁。

**审查暂缺时**：可实现、测试、冻结候选并推任务分支供 Pro/后续审查读取；不能自审合 main，也不能把新 zcode 会话伪称跨工具审查。H 无人可审时准备简短升级包并切换其他 READY 支持任务，不把 Codex 设成日常常驻依赖。Pro 可读到固定代码/证据时作其能力范围内的复核，但不能豁免本地实测或未看过的画面。

未接入生产的独立基础模块可以单独交付，但必须证明无导入/初始化副作用，仍按该模块自身风险和适用审查走流程，不是绕过批准的快速通道。

**待视觉验收的生产切片最多2个**。达到上限后不继续堆用户可见新功能；可继续已批准来源的只读核验、独立测试夹具、数据加工验证、证据整理和现有切片缺陷修复。依赖未批准 H 契约的支持成果标依赖，不接入生产路径。过去已合并的 P1 等若缺独立视觉复核也计入待验队列，不通过重写历史抹掉。

## 文件与契约所有权

同目录同一时间一位业务作者。SolarEngine、CameraController、BodyPoseProvider、contracts、公共地形/瓦片管理器、App、锁文件、来源清单和验收 runner 属共享热点；每张任务卡明确本轮所有者及允许范围。即使改不同文件，也须共用同一单位、姿态、颜色、时间和资源语义。

第二作者加入后使用短任务 worktree，不建长期 zcode/anti 产品分支。不同 worktree 仍共享 refs/config，不是权限沙箱。禁止切换/清理其他活跃目录或结束别人的进程。新任务只从记录清楚的已验收基线或明确依赖的冻结候选分出，后者在上游未批准前不可独自发布。

## 证据和串行集成

1. 作者交付 task head T，值班集成人记录当前 main B，在独立候选目录组合得到 C（若本身为直接后继可明确 C=T，仍检查 B→C 的完整范围）。审查时冻结 C。
2. 在 C 上运行适用检查并独立评审。改动、主线基准或相关资产改变则旧批准失效；Git 冲突由明确作者处理，不盲选 ours/theirs。
3. 每次验收标记 code SHA/source tree、资产 manifest/hash、时间/天体/站点、相机/FOV、曝光/模式、浏览器/GPU/分辨率、真实 UI 输入路径。PASS/FAIL/BLOCKED/NOT_RUN 分开，没看过图写 NOT_OBSERVED。
4. 自动检查须有独立预期和失败出口；不能从被测实现抄一组常量、写死 PASSED、隐藏控件或调用私有 API 代替真实 UI 入口。像素非黑只能反证黑屏，不能证明地形真值或视觉质量；性能区分 engine 帧/CPU/GPU。
5. 唯一值班集成人确认适用的独立批准、证据和当前 B 后才推进 main；同一作者换"集成人"称呼不获得批准权。同 GitHub 账户的角色记录不伪装成独立账号审批。
6. 只正常推送/受控合并，不 force、不跳闸门；最终树与候选不同就重新验证。只更新无人编辑的稳定体验目录。回退用明确提交的 revert。

冻结候选不能含引用自身 SHA 的文件。报告后写，关联 candidate/source tree/asset hash，记录纯证据提交与被测产品提交的差别。`check-packet.mjs` 只检查给定声明与文件哈希一致，不执行测试、不验证身份、不批准合并。

## 额度中断、恢复与阶段审查

每个验证单元或上下文/额度边界留下：任务、owner、目录/分支/HEAD、未提交/未跟踪/忽略的必要数据、最后真实验证、失败/未测、PID/端口、资源占用、下一最小动作。原作者停止写入且接手者确认后才移交。

Anti 恢复后先读队列，独立检查积压固定候选，再领取契约明确的视觉实现卡，不重复建设已经完成的工程。初期最多两位实现者、一个串行集成候选；GPU 性能测量只运行一个负载。

两次不同假设的具体验证仍无法解决的技术争议，或新的核心语义取舍，提交两页以内的 base/candidate、复现、少量相关文件、证据、两个方案与需要判断的问题给 Codex/Pro。普通实现不调用 Codex，每次新会话不重灌全部聊天。

一个完整可玩切片形成后再请 Pro 阶段深审；给 Zac 一个稳定入口、一段代表录像、2–4张版本明确的图、最多3个体验取舍问题。公开仓库可放经过检查的必要代码与证据，不上传原始聊天、账号资料、浏览器配置或本地备份；公开部署、外部付费仍另按授权。

## 通过公开链接审查

仓库公开后，优先将仓库网址和完整 commit 发给 Pro。公开网页访问无需私有仓库连接授权，也不要求为此启用 GitHub 插件。

公开的是 Git 已跟踪并推送的内容，不包括本地未提交、未推送或被忽略的文件。它也不会自动把全仓库载入模型上下文。要求模型实际读取源码、报告覆盖范围；工具无法读取的文件应明确列出。

如果模型具备下载解包能力，可让它读取固定提交的完整 GitHub 源码归档：`https://github.com/zacmememe/solar-system-explorer/archive/<完整commit>.zip`。该归档包含此提交的所有已跟踪文件，与本地精简审查包的选择范围不同。无法下载或解包时，改为逐文件读取并报告缺口。

## 一键生成材料

Windows 可直接双击项目根目录的 `导出Pro审查材料.bat`；它导出 HEAD 并附带已有的预选截图。若要包含尚未提交的修改，使用下面的 `--working-tree` 命令。

双击入口会寻找已有的 Node.js；导出脚本会寻找已有的 Git，包括本机 Codex 自带的 Git，不修改系统 PATH。成功时显示 `SUCCESS:` 和新 ZIP 的完整路径；`review-exports/LATEST.txt` 始终指向最近一次成功导出的文件，失败不会更新它。目录里的旧包会保留，因此看到文件不等于本次执行成功。

```powershell
# 推荐：导出刚提交、推送的 HEAD
npm run review:export

# 比较两轮：输出指定基线到 HEAD 的文本差异
npm run review:export -- --base 上一轮commit

# 加入已有画面证据；导出不会运行浏览器或重新截图
npm run review:export -- --with-images

# 临时讨论尚未提交的实现，材料会明确标为工作区快照
npm run review:export -- --working-tree
```

输出在项目 D 盘目录下的 `review-exports/`，不会纳入 Git。Windows 还会生成同名 ZIP。可上传 ZIP；也可上传 `REVIEW.md` 和全部 `source-context-*.md`。包内保留按原路径存放的源码及 SHA-256 清单，便于定位。

默认包括当前 `src/`、`tests/`、`scripts/`、`docs/`、`sources/` 和核心配置；不包括依赖、构建产物、原始聊天、历史交接包、凭据和大体积纹理二进制。纹理文件另有路径/哈希清单。`--with-images` 仅加入预选的少量已有 PNG，文件时间不等同于拍摄时对应 commit，需自行确认。

工作区导出可能包含新增文件。脚本会检查常见凭据特征并拒绝明显敏感文件名，但不能替代人工检查。导出期间请暂停编辑；脚本检测到选中文件在读取过程中变化时会中止。

导出不运行测试，也不将过去的测试报告标成当前通过。将本轮真实执行的命令、结果及画面问题补充给 Pro。

## 本机 GitHub CLI

已有 CLI 位于 `D:\Apps\GitHubCLI\2.101.0\bin\gh.exe`，配置目录为 `D:\Apps\GitHubCLI\config`。需要使用 CLI 时：

```powershell
$env:GH_CONFIG_DIR = 'D:\Apps\GitHubCLI\config'
& 'D:\Apps\GitHubCLI\2.101.0\bin\gh.exe' auth status
```

不要将 CLI 登录令牌复制到项目、提示词或审查材料中。

本机已在这个仓库的本地 Git 配置中指定上述 CLI 和 D 盘配置目录，因此普通 `git push` / `git pull` 不需要手动设置 `GH_CONFIG_DIR`。该配置不含令牌，也不影响其他项目；若将来移动或移除该版本的 GitHub CLI，应相应更新本仓库的 credential helper。
