# 亲子太阳系漫游：重建方案与可行性分析

研究日期：2026-09-20

文中 `[Sxx]` 对应 `sources.json` 的官方或一手来源。未附来源的架构、预算、验收阈值和排期，是本项目的设计建议，不代表既有系统实测结果。所有 API 版本、依赖与原图链接在正式开发时再次核实并锁定。

## 1. 结论与产品边界

可以做出明显超过旧版本的体验，但路径应是把一个小型、完整的太阳系探索产品做好，而不是从零开发通用宇宙引擎。

新版最有价值的升级是：

1. 把“真实贴图”升级成有来源、投影、观测波段、覆盖局限和处理记录的素材系统。
2. 把“飞到球旁边”升级成稳定、可打断、可保存、能够理解空间关系的观察体验。
3. 把“很多星球”升级成几个真的值得停留的地方：地月系统、土星环与冰卫星、木星及四颗主要卫星。
4. 把“做得出来一次”升级成能测试、备份、重建，不再依赖一台电脑。

目标使用方式是家长和孩子一起看一块屏幕，孩子能指出想去哪里，家长可以辅助操作；不能默认孩子已经识字、会组合快捷键，或愿意先学飞船驾驶。

首发假设：Windows 桌面浏览器优先；中文界面；鼠标/触控板可玩；可在本地启动，也可部署为静态网页；平板适配随后验证。没有依据认定具体显卡性能，M0 必须测环境。

### 1.1 从旧截图能够确定的内容

旧版本已展示目的地选择、附近卫星、时间加速、全景入口、信息卡、“飞往这里”和飞行器选择。土星环、土星与土卫六构成了强烈的前后景关系。

代码编辑器截图保留了更重要的旧经验：不自动重置相机；真实素材优先；保持缩放机制一致；土星环需要特殊 UV 处理；区分点击和拖动；每次修改后到浏览器验证；优先改现有代码、不重写；以中文沟通。

这些是可以继承的需求，不是已经恢复的代码。截图中“使用对数函数保持相对比例”不能按数学意义原样继承：对数压缩会改变比例。新版保留对数缩放的手感和尺度层级，但把压缩展示与真实比例明确区分。

第一张早期图的星环上有文字状异常，仅凭截图不能确定是资产误载、图幅标注还是 UV 错误。应将它转化为资产与 UV 的回归测试，不臆断根因。

家庭视频的可见画面体现共同观察和孩子指向屏幕。没有依据从短视频推断长期使用频率、学习效果或完整功能。

### 1.2 新版不继承的限制

卫星不应只是一颗换皮小球。土卫六的厚雾外观与红外表面需要分开；一张红外地图不能被描述成肉眼能看见的表面。[S08–S10]

信息卡的数据名称必须准确。旧图出现过“距太阳”字段与“距土星”数值放在同一格的情况。新版分别定义父天体、当前距父天体、平均轨道距离、当前距太阳，禁止复用一个模糊 distance 字段。

“真实素材”不意味着光照、观察位置、行星大小、轨道距离和动画耗时全部真实。要逐项定义，而不是全局贴一个“真实太阳系”标签。

## 2. 参考产品：借什么，不借什么

| 参考 | 经核实的特点 | 本项目可借鉴 | 不作为首发范围 |
|---|---|---|---|
| NASA Eyes on the Solar System | 浏览器 3D、天体和任务、时间探索、真实数据与图像 [S01] | 目标导航、科学上下文、选定事件/时间的观察入口 | 数百任务、航天器历史轨迹全集 |
| Solar System Scope | 太阳系/夜空模型，另提供贴图库 [S02–S03] | 易理解的目的地组织、素材启动路径 | 直接照抄界面或把其素材全部叫原始照片 |
| SpaceEngine | 宇宙尺度旅行，真实目录与程序生成并存，支持保存位置 [S04] | 飞行节奏、取景、空间收藏 | 无限宇宙、全球地表着陆、程序生成地貌 |
| Celestia | 开源桌面空间浏览项目，代码 GPL-2.0-or-later [S05] | 作为已有方案与体验基准 | 默认把桌面代码直接变成易维护网页；忽略代码/资产许可区别 |

推荐独立的小型 Web 项目，而不是修改一个大引擎。需要借的是可验证的交互原则，而不是承担原产品所有复杂度。本次没有在用户机器实测上述应用；它们能证明相关交互形式已经存在，不能直接证明新工程能达到某个帧率。

素材与渲染工具并非都是今年才出现。月球 CGI Kit 确有更新资源可用；很多 Cassini 地图早已发布。新版的进步主要来自挑选、整合、约束和验证，而不是把“最新”当作质量保证。[S06–S10]

## 3. 首发范围：17 个目的地，分批实现

17 个核心目的地 = 太阳 + 八大行星 + 月球 + 木卫一/二/三/四 + 土卫一/二/六。

月球、木卫一 Io、木卫二 Europa、木卫三 Ganymede、木卫四 Callisto、土卫一 Mimas、土卫二 Enceladus、土卫六 Titan 的 ID 与双语名称集中管理，不用显示名作为程序主键。

M1 只有地球和月球。M2 加入土星、土卫六、土卫二，形成完整的高质量局部样片，并为需要运动的土星卫星准备一个经过检查的短星历窗口。M3 再拓展其余目的地与数据覆盖。M2 若暂用固定日期场景，就明确显示该日期并限制时间控件，不能先把任意摆位称为当前真实位置。范围少不等于使用临时灰球、低质交互或没有测试。

### 3.1 必须完成的体验

选中天体、看到简短卡片、主动飞近、旋转观察、缩放、暂停或改变模拟时间、查看附近卫星、返回全景、打开来源说明、保存一个观察位置。

M4 完成照片/明信片与本地探索记录。飞船先作为可选的轻量角色或界面标识，而不是带发动机、燃料和动力学的系统。截图中出现飞行器选择，不代表必须把多飞船定制当首发核心。

### 3.2 明确延期

无缝行星地表着陆；真实驾驶/引力弹弓；多体引力积分；太阳系外星系；VR/AR；联网多人；开放式儿童 AI 聊天；账号与云存档；全太阳系任意历史日期精确回放；全部小行星和全部卫星；全天体 8K 常驻；无限粒子的星环与小行星带。

延期并非技术上永远不能做，而是这些项目会改变架构、素材量或测试边界。加入前必须独立立项。

## 4. 一条应当做出来的亲子体验

启动后显示可辨认的地球和月球，不要求先阅读教程。界面只保留“去哪里”“暂停”“看全景”。

孩子选择月球。第一次点击只选择，出现简短名称和“飞往这里”；相机在用户明确发起后才移动。飞行用 2–5 秒的取景过渡作为初始调参区间，拖动立即中断，不播放强制倒计时。到达后镜头保持用户控制，能看见月海和陨石坑纹理。

然后选择土星，经过一次明确的场景转换进入局部系统。先看到有明暗层次的环，不用密集星点抢走注意力。孩子可自由绕到环的另一侧；“换个推荐观察点”必须由用户按下，不能自动转走。

选择土卫二后，主体转为一颗带裂纹的冰卫星。父行星在背景中的角大小与观察位置相符。可主动开启“增强色观测”理解裂纹；羽流在后续阶段作为有说明的视觉示意，而不是伪造的实时观测。[S07]

选择土卫六：默认呈现有观测依据的厚雾外观示意。用户打开“红外观察”后看到有出处的表面亮暗图，提示“这种光能帮助探测器透过雾看到表面”。若使用 938 nm 的灰度图，就明确称近红外图，不冒称 VIMS 彩色地图。[S08–S10]

最后保存一个视角或拍一张明信片。“今天去过哪里”只记录已访问，不以积分、连续签到或答题门槛干预自由探索。产品的结束可以是“留住今晚喜欢的画面”，不是必须把太阳系学完。

## 5. 科学口径：五件事分别标注

| 维度 | 默认策略 | 显示方式 |
|---|---|---|
| 天体外观 | 可追溯观测拼图或有说明的外观重建 | 真实观测/增强色/红外/观测约束示意 |
| 尺寸 | 局部与近景尽量统一线性比例 | 全景尺寸放大时显示“大小已放大” |
| 距离 | 全景可压缩，局部使用统一线性比例 | “导航示意·距离已压缩” |
| 位置与运动 | 解析星历或离线星历，声明有效窗口 | 当前日期 + 位置模型状态 |
| 旅行方式 | 为观察设计的相机过渡 | 不宣称真实飞行速度或耗时 |

信息卡默认只有名称、一句观察提示、一个行动按钮。详细数据放折叠层，包括来源及数据类型。孩子主界面不需要同时理解所有标识，但家长必须能一键查看。

月球和卫星的“真实表面”可以是多时刻、多波段、多任务拼接，不等于单张自然光照片。观测缺口需要保留或标明。不能将亮度图自动解释成高度图；不能从无地形数据的纹理生成法线后宣称真实山脉。

### 5.1 数据模型约束

每个科学数值使用明确单位和来源。半径要说明平均/赤道口径；轨道距离区分平均与瞬时；温度不能只给一个没有昼夜/测量条件的数字。M1 不必要的数据宁可不展示。

轨道位置质量与自转朝向质量分开。仅有可靠公转坐标，不代表已经精确模拟该卫星的本初子午线、章动和物理天平动。未验证的姿态采用“自转示意”，不把局部地貌指向当作精确科学结论。

## 6. 推荐架构：一个静态 Web 应用，不要通用引擎

建议 Vite + TypeScript + Three.js，React 仅负责菜单、卡片和状态显示。Three.js 的动画循环、天体对象与相机由独立模块管理，不能因为 React 重渲染而重建整个场景。

采用 WebGLRenderer 作为首版唯一渲染路线，目标 WebGL2。当前 Three.js 的 WebGPURenderer 已可在不支持 WebGPU 时回退到 WebGL2，说明 WebGPU 不是不能用；选择 WebGLRenderer 是为了降低首版材质和测试分叉，不是断言 WebGPU 不成熟。[S16–S17]

不默认加入 Next.js 服务端、数据库、全局状态库、游戏 ECS、物理引擎或渲染 Worker。先用一个小型状态容器和命令接口；在数据证明有必要时再引入额外依赖。

Vite 的 Node 与浏览器要求以初始化时官方文档和选中版本为准。固定具体版本及 lockfile；不得引用旧教程后无声混用不同 Three.js 示例版本。[S20]

### 6.1 最小职责分工

| 模块 | 唯一职责 | 禁止行为 |
|---|---|---|
| BodyCatalog | 天体名称、半径、父子关系、素材、数据来源 | 把渲染比例写回真实半径 |
| EphemerisProvider | 输入时间，输出位置/速度及质量 | 每帧联网 |

| CameraController | 选择响应、飞行、跟随、缩放、视角保存 | 多处写 camera 或隐式自动取景 |
| AssetManager | 加载、缓存、校验、释放 | 晚到回调切回旧天体 |

M1 只需实现实际用到的职责，可以先合并小文件。表格是边界，不要求先创建八个复杂框架。

## 7. 最大工程难点一：比例、坐标与空间感

### 7.1 三种展示状态，不是一套比例走到底

全景用于找到目的地：压缩日心距离，可以放大图标或天体，显示导航示意。保留轨道层次和方向，不宣称准确尺度。

局部系统用于理解关系：地球/月球、木星/卫星、土星/卫星，以父天体为局部原点，位置和几何尺寸使用同一个线性换算。太小的卫星用可点选标记帮助发现，不偷偷把实体放大成同样大小。

天体近景用于观察：相机定位在目标附近，保持该域的线性比例；父天体背景的角大小应由距离和镜头决定。禁止“无论在哪里父行星都铺满屏幕”。需要电影化构图时，可以主动使用特写镜头或单独的示意场景，但要与真实位置观察区分。

跨系统过渡允许短淡入/淡出或连续感动画，并明确它是旅行可视化。首版不要求一个相机在单一坐标域从太阳连续移动到海王星还保持毫米级精度。

### 7.2 保留双精度科学数据，给 GPU 局部坐标

JavaScript number 存公里级物理数据；送入 GPU 前先减去当前系统/相机附近的原点，再按局部比例缩放。不可先把巨大的绝对坐标写进 float32 buffer，再试图相减挽回已经丢失的精度。

```text
relativeKm = physicalPositionKm - focusOriginKm
renderPosition = fixedBasisTransform(relativeKm) / kmPerSceneUnit
renderRadius = physicalRadiusKm / kmPerSceneUnit
```

同一帧内所有相关对象使用同一个原点和基底变换。轨道线、标签、拾取坐标、阴影方向同步转换。

科学层统一采用 J2000 赤道参考方向的笛卡尔坐标；渲染层可以一次性变换成便于观察的黄道朝上坐标。不要对不同来源分别猜 Euler 角后拼在一起。视参考系、位置原点和天体固连参考系是不同概念。

### 7.3 场景层级必须避免的错误

```text
localSystemRoot（只负责系统平移/统一坐标变换）
  parentBodyPosition
    parentBodyFixedOrientation
      parentSurface
      parentRings
  moonPosition（来自物理坐标，不挂在 parentSurface 下）
    moonBodyFixedOrientation
      moonSurface
```

否则行星一天自转一圈时，卫星也会错误地绕它一天一圈。潮汐锁定卫星应近似朝向父行星，而不是朝相机或太阳；第一版未做精确姿态时明示近似。

近远裁剪面随局部域调整。先用局部坐标解决大尺度问题，再评估对数深度或反向深度。Three.js 提供有关选项，但它们不代替正确坐标架构。[S16]

## 8. 最大工程难点二：相机必须只有一个主人

相机状态建议 `OVERVIEW`、`ORBIT_TARGET`、`TRANSITION`，自由驾驶 `FREE_FLIGHT` 放后续。状态是工具，不要再叠加多个互相竞争的控制器。

选择天体仅更新 selectedBody。主动点击飞行才更新正在观察的目标。卡片关闭不意味着退出观察。纹理加载完毕只换材质，绝不“重新把天体摆正”。

### 8.1 飞行与控制

到达距离按天体包围范围、屏幕横纵视角和留白计算。土星的范围必须包含环，不能只按球半径。天体包围球半径为 R、半视角为 α 时，完整容纳的起点可用 `distance >= R / sin(α)` 加安全边距；再按构图调整。注意横屏和竖屏取更限制的半视角。

飞行先实现有限时长、平滑缓入缓出和明确的起终点。不能直接从一颗球内部穿过去：同一局部域为路径增加安全外侧航点；跨系统允许场景过渡，不承诺轨道动力学真实。

新飞行有单调增加的 commandId。用户拖动、缩放或发起新飞行时取消旧命令；旧异步回调即使到达，也不能夺回控制。飞行进度用真实经过的秒数，公转使用模拟时间，两者分开。

到达运动天体后，相机/控制目标随天体平移，但保持用户选择的相对方位；默认不随着行星自转。必要的阻尼只在用户输入后产生，不作为“自动回正”。

点击/拖动按 pointerdown/up 位移和多指状态区分。可先以 6 CSS 像素为鼠标拖动阈值，再真机调节；阈值不是科学常量。UI 点击不能同时触发后面的 3D 拾取。

### 8.2 保存什么

保存 targetId、当前模式、目标局部相机偏移/方位、距离、视场角、模拟时间、观测图层、质量档位及 schemaVersion。不能只保存会因换原点而失效的全局 camera.position。

恢复书签是主动操作，允许取回冻结日期；不能因为云/纹理更新自动覆盖书签。存档导入必须校验合法值，无法识别字段时安全回退并给提示。

## 9. 真实贴图与视觉管线

详情见 `02-ASSETS.zh-CN.md`。核心原则：真实来源、正确加工、稳定加载、正确解释，四件事缺一不可。

地球从真实来源的白昼、夜间与云图分层入手；初版云图是固定时刻的图像，不称实时天气。月球优先 NASA CGI Moon Kit。土星及环可用已署名的 Solar System Scope 启动；土卫二使用 Cassini 地图；土卫六区分自然外观示意和近红外观测。[S03, S06–S10]

### 9.1 先做好五个视觉细节

第一是昼夜分界与明暗层次。不能用强环境光把背面全部照亮，也不能为“物理真实”让孩子只看到黑球。提供明确的教学提亮档位，别把它说成真实曝光。

第二是土星环。使用环几何和径向纹理映射，而不是给圆盘直接铺一张矩形图。对环平面局部坐标，`u = (length(xz)-innerRadius)/(outerRadius-innerRadius)`，v 固定在条带中部；若环的局部平面是 XY，公式要相应调整。读取 RGBA alpha 的含义，确认条带哪端是内环，再实现双面与遮挡。不能把文件名带 alpha 当作已经检查过透明通道。[S18]

第三是阴影。土星遮住背后星环、星环影响行星受光，是 M2 的高价值目标。先完成球体/环的几何遮挡，再做有限的解析投影或稳定阴影方案。不用实时光线追踪作为前置条件，不把环纹理 alpha 当作实测光学厚度。

第四是大气。地球用轻量边缘散射外观；土卫六用与观测一致的雾层外观。程序化大气渲染可以是有标注的物理/视觉近似，不等同于虚构表面地貌。自然外观默认遮蔽土卫六表面，而红外模式主动揭示观测地图。

第五是克制的星空与曝光。星点固定随机种子或使用有来源的背景图；亮度和密度不能盖过星球。装饰星空不作为精确星座图。默认禁止大面积紫色星云、夸张镜头光斑和长时间高速旋转。

### 9.2 着色数据不能混用

颜色贴图按其说明处理 sRGB/linear；法线、高度、粗糙度与遮罩通常作为非颜色数据处理。读取具体资产说明，不用“所有贴图统一 sRGB”。[S06, S16]

没有真实 DEM 时不从陨石坑的明暗直接合成“真实地形”。正常渲染可先不使用置换。即使月球已有 DEM，首发仍先用基础表面或正确的法线；全球细分位移、地表着陆放后续。

有烘焙明暗的拼图可能与动态太阳方向冲突。先记录限制、控制凹凸强度，选择更合适的反照率图；不擅自擦掉地貌或做生成式补全。

## 10. 星历、时间与离线数据

推荐主行星/月球及木星四大卫星优先通过 Astronomy Engine 适配。项目提供 JavaScript 等实现和相关坐标能力，木星卫星支持应按固定版本接口验证；不能假定它同时覆盖土星卫星。[S13]

土卫一/二/六使用 JPL Horizons 在构建阶段下载相对土星的几何位置和速度表。先用短窗口验证，再生成发布窗口。不要从零写 N 体引力模拟，也不要把百科的公转周期直接等同于“某时刻真实位置”。[S14]

### 10.1 Horizons 获取约定

在本地脚本中按官方接口查询并核实目标 ID、中心 ID。使用 VECTORS（笛卡尔几何状态），不是给望远镜用的方位/高度表。设置参考平面/参考系、中心、单位、时间尺度、位置速度输出和校正方式。

推荐内部规范：公里、秒、现代日期 UTC；若接口选择 UT 输出，必须核对返回时间说明并在适配层明确映射；若保留 TDB，就由适配层统一转换，禁止简单把 TDB 字符串后加 Z 当 UTC。参考方向用 FRAME/ICRF 并校对与应用 J2000 赤道规范的一致性。

API 的 JSON 包装可能在 result 内包含文本表格；以实际响应为准，验证签名、版本、目标名称、参考中心以及 `$$SOE`/`$$EOE` 数据段，不能假定 result 已是数值数组。

JPL 明确要求单次只发一个请求、缓存与复用、失败退避、有效应用 User-Agent，并禁止在网页直接嵌入这些 API。构建期采集、运行时同源读取静态数据正好符合项目需要。[S15, S25]

### 10.2 插值和有效期

土星卫星先尝试 30 分钟采样和位置/速度三次 Hermite 插值。这个步长是待验证起点，不是已证明满足全场景精度。用采样中点及随机时间直接查询值做对照，必要时缩到 15 或 5 分钟。把最大误差、样本数与查询条件写入构建报告。

第一批数据只做 7–30 天验证。发布时可扩展到约 90 天或一个明示的日期窗口。时间选择器不得越过相关卫星数据覆盖范围；越界时提示并停止推进，或在用户主动选择后进入明确的近似演示模式。不得无声外推或循环播放旧日期。

切换 tab 时默认让探索时间自动暂停以防失控，并区分用户暂停与“页面在后台”的临时暂停原因。恢复时保持原选择和镜头，按照产品决定是否恢复原倍速；不要把失焦的几小时突然累计到当前画面。

开发与截图测试固定模拟日期，便于比较。显示“今天”时核对当前日期在支持窗口内。太阳系位置只说明模型计算的状态，不暗示来自实时相机。

## 11. 性能计划：先测，再升级

以下是初始预算，不是已达到的指标。

| 项目 | 桌面默认目标 | 首选处理 |
|---|---|---|
| 分辨率 | 1080p 视口，DPR 上限先设 1.5 | 独立调节渲染分辨率，不缩小 UI |
| 帧率 | 常规观察争取 60 fps；低档稳定 30 fps | 看帧时间分布，不只平均值 |
| 首次可交互 | 20 Mbps 测试网络下争取 5 秒内 | 首屏资产压到约 6 MB 以内，延后非当前素材 |
| 贴图精度 | 2K 入场、当前主角最高先 4K | 有效源精度不足不虚假升采样 |
| 纹理 GPU 预算 | 桌面先以 256–320 MiB 为上限区间 | 用估计值与对象数量监测；不冒称精确 VRAM |
| 移动低档 | 1K/2K，DPR 1，少后处理 | 真机验证，不只开发工具模拟 |
| 稳定性 | 连续玩 30 分钟无未处理错误 | 循环切换、丢网、隐藏 tab、上下文恢复 |

8K 的文件体积小，不表示显存小。RGBA8 的 8192×4096 纹理本体为 128 MiB，完整 mip 链约 170.7 MiB；4K 对应约 42.7 MiB。这里是像素格式下的理论计算，不是特定浏览器的实测分配，且未算帧缓冲等资源。

首版先做按需加载和释放，再决定是否引入 KTX2/Basis 压缩。Three.js 有 KTX2Loader，可按 GPU 能力转码；需要同版本的解码资源与支持检测，不能只把 JPG 改后缀。[S19]

### 11.1 缓存规则

只锁定当前主角、需要显示的父天体和小量邻近目标；其余低精度或释放。采用基于估计字节的 LRU，而不是所有天体永久常驻。频繁访问的目标可保留低精度版本，高精度先淘汰。

纹理替换前准备低清底图；资源失败有错误状态与重试按钮；一次只预取有限数量。取消不一定能终止所有底层图片解码，但旧结果必须被 commandId/目标版本拦住，不能修改现在的选择。

共享纹理/几何用引用计数或明确拥有者；只在无人使用时 dispose。React 开发模式的重复挂载必须正确清理事件、动画循环和 GPU 资源。`renderer.info` 主要提供对象数量和绘制统计，不把它当完整准确的显存分析仪。[S16]

性能降档首先降低 DPR、后处理、云层复杂度和纹理分辨率；不得为了帧率清空用户的书签、镜头或真实素材出处。

## 12. 里程碑、依赖与停止条件

工时表示有效开发/检查时间的规划区间，包括 AI 迭代和人的验证，不等于模型生成代码所花时间；不能在不知道操作者和环境时当交付承诺。

| 里程碑 | 工时起点 | 产出 | 进入下一阶段的条件 |
|---|---:|---|---|
| M0 环境/资产 | 4–8 小时 | 可启动页面，地/月资产验证，依赖锁定 | 本地启动和资产校验通过 |
| M1 地球/月球 | 8–16 小时 | 完整选择/飞行/观察/暂停链路 | 操作不回正，拖动不中招，真实素材可见 |
| M2 土星样片 | 12–24 小时 | 土星环、土卫六、土卫二、两类观测 | 从正/背/侧面看都正确，不靠摆拍角度遮错 |
| M3 核心内容 | 12–24 小时 | 17 个目的地、统一数据、星历窗口 | 名称/来源/单位校验与坐标对照通过 |
| M4 亲子体验 | 12–20 小时 | 短提示、明信片、书签/记录、基础触控 | 家长孩子可连续探索，不需要重载解救 |
| M5 性能/发布 | 8–16 小时 | 质量档、静态发布、存档导出、恢复演练 | 真机试玩、30 分钟压力测试、干净重建通过 |

基础合计 56–108 小时，另预留约 25% 的素材、图形与环境问题缓冲，即约 70–135 小时。若要真实全球地形、精确姿态/食变、原生移动端或全场景 WebGPU，这个估计不适用。

一次 Shader/阴影尝试连续几个迭代没有清楚进展，应缩小为独立测试场景，而不是继续往主工程加补丁。首版可以暂时没有复杂大气、真实羽流和环微粒，但不能没有正确贴图、稳相机与基本环遮挡。

17 个目的地不能绑架 M2：M2 若尚不能从多个角度稳定展示土星系统，不进入内容铺量阶段。

## 13. 验证：编译成功远远不够

详见 `03-ACCEPTANCE.zh-CN.md`。单元测试负责坐标、时间、状态机和清单校验；浏览器测试负责点选、飞行、打断、保存与恢复；人工负责视觉真实性、舒适度和孩子的可理解性。

Playwright 支持截图对比，但字体、平台、浏览器和 GPU 都可能影响结果。固定环境、日期、随机种子、视口及动画状态，对小范围渲染差异设置容忍；不能要求所有机器逐像素一致，更不能看到差异就机械更新基线。[S21]

验收时至少保存地月、土星环正面、环背面、近环平面、土卫六自然外观/红外、土卫二等固定场景。测试必须能证明在切换、拖动、等待和加载失败后仍正常，而不是只截图最漂亮的一帧。

家庭试玩观察三件事：孩子是否知道怎么去下一站；画面变化是不是由自己或家长主动控制；是否有愿意停留观察的地方。不要用短视频或一次试玩宣称认知能力提高。

## 14. 部署、隐私与不再丢项目

首版无运行时后端、无付费 AI API、无账号。所有核心贴图、解码器和星历放同源静态资产，不热链 NASA 或其他网站。开发期外网获取与游玩期联网依赖分开。

本地版通过本地 HTTP 服务启动，不承诺双击 index.html 就可运行 ES 模块与资产。在线静态版可以部署到常见静态托管，包括 Vercel；成本、配额和地区可达性在发布时检查，不在本方案中保证永久免费。先本地玩通，再部署。

离线支持是单独验收项。早期提供包含已审核资产的本地可运行包；PWA 缓存后续按明确“下载离线包”实现。Service Worker 要有版本化、更新提示和缓存清理，不能用它掩盖文件缺失。浏览器存储可能被清理，不能当唯一存档备份。

代码每个可运行里程碑提交 Git；远端仓库需由用户明确配置授权。原始大图和发布素材另有完整备份，源链接与哈希不是文件本身，也不能保证远站永久存在。不要认为 Git LFS 指针已等同于原图备份。

每次阶段发布保留：源代码、lockfile、构建说明、生产资产、原始资产的备份位置、来源/许可、星历原始响应与转换数据、测试报告、存档导出格式。家庭媒体默认不进仓库。

最后做一次干净恢复演练：换空目录拉取代码，恢复资产，执行锁定依赖安装与构建，断开外网后从本地服务启动，导入一个书签。这个演练通过，才算解决了本次重建最痛的风险。

## 15. 还未验证的事情

没有恢复原项目算法、贴图文件与网址，也不能仅凭图像判断当时是不是使用某个公开贴图库。

已打开并检查一些候选原图预览，但没有将全部文件下载到用户环境；本研究容器的一次网络下载尝试出现 DNS 失败，因此不提供假造的字节数、哈希或“资产已入库”结论。

NASA/USGS 科学资源中有些下载入口需要额外定位、转换或网络重试。候选目录将“可用的起步来源”“需要裁切的图幅”“仅参考的展示图”“尚待确认的数据入口”分开。

所有性能预算还要在目标电脑及实际平板验证。离线星历接口规范已查阅，但本包未生成经过误差验证的星历数据。许可页面已核实，不代替逐件资产及发布用途审查。

最先应证明的，不是已经有 17 个按钮，而是孩子能选择月球、自由地看它、飞往土星、主动揭开土卫六的雾，再安全回到喜欢的画面。
