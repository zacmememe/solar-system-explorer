# 航天器载具系统：产品定义与工程方案 v2

研究日期：2026-09-20。用途：交给本地 AI 实施。本文是设计与验证计划，不是已实现游戏。

## 0. 对上一版的正式修订

用户明确把人类经典、当代、未来航天器——包括无人探测器与太空望远镜——作为可切换载具和项目特点。因此废止旧方案“飞船只是可选轻量UI/角色，不作为首发载具系统”的限制。载具和目的地是并列内容维度，从第一轮工程设计就接入。

保留原方案：Vite+TypeScript+Three.js，React只管UI；WebGL2首发；17个核心天体分批交付；相机不自动回正；真实数据与显示尺度分开；短迭代、实际浏览器验收。

仍不默认承诺：每艘真实座舱、真实推力/燃料/引力弹弓、全地表着陆、完整历史轨迹、全部航天器一次上齐。这里削减的是模拟深度，不是取消乘坐、切换和载具可见性。

## 1. 产品的两个并列入口

“去哪里”管理天体和观察区域。“乘坐什么”管理航天器。孩子能先选星球再选船，也能因喜欢一艘船而寻找它的任务。机库可单独进入，不需要先选目的地。

一轮完整体验：打开机库 → 旋转看飞船 → 看懂载人/无人/概念标签 → 明确点击“使用这艘” → 在当前地点出现载具 → 选择目的地 → 伴飞/虚拟随船视角出发 → 到达后自由观察 → 主动展开它与此处相关的故事或影像 → 保存“今天乘坐……”的明信片。

首发载具不是菜单图标，也不是屏幕角落永远贴着的PNG。至少有真实3D外观、游戏中的空间位置/姿态、伴飞视角、虚拟随船视角、在当前世界切换、来源和内容档案。

## 2. 真实与想象如何共存

### 2.1 自由探索（默认）

所有已验收载具共用舒适的旅行控制；允许载人舱、无人探测器、望远镜去游戏支持的任意地点。页面轻量常驻“自由探索·虚拟航行”。这里的秒级跨行星旅行不代表真实飞行能力，不增加机械的燃料限制、等待时间和机型解锁。

无人器具显示“虚拟随船视角”，不虚构驾驶员座位。望远镜可以作为想象中的旅行载具，但不把它的外部观察点称为真实驾驶舱。虚拟乘坐不需要否定孩子的想象，只需不把想象写成航天事实。

### 2.2 任务故事（首发少量，数据驱动）

短观察提示、结构热点、真实档案影像、与天体的关系组成独立内容包。需要世界坐标的故事可以使用明确标记的示意位置；只有通过数据验证才能标记“历史位置重现”。故事先1–3个，不写数十套专属小游戏。

卡西尼与土星系统是优先主题。Huygens是独立探测器/构型，而非任意时刻都挂在Cassini上的装饰。[V07][V31]

新视野号可先作为自由探索载具使用，冥王星的全3D目的地不随模型导入自动加入；归档图片卡不依赖扩展宇宙。[V15]

### 2.3 历史航迹回放（后续独立适配器）

位置来自经确认的离线星历/任务数据；姿态来自独立来源。SPICE的SPK与CK分工不同，知道位置不等于知道当时天线或相机朝向。[V28][V29]

只针对一段短遭遇窗口制作首个样例，不一开始重建全寿命任务。保存源kernel版本/校验和、coverage、参考中心、frame、时间尺度、单位、几何/光行时校正和误差检查。CK有缺口就显示姿态示意，不把速度方向充当真实姿态。由ET/SCLK转到项目时轴须保存转换依据；必要的LSK/SCLK/FK/IK/PCK也要归档。

进入回放明确改变“当前模式和时间”；退出恢复进入前的自由探索存档。换成非任务飞船时应退出或明确是想象旁观，不能继续标为史实回放。默认不对接实时API。

## 3. 载具目录和内容深度

类型：载人舱/轨道器、登月舱/着陆器、飞掠探测器、轨道探测器、空间望远镜、旋翼器/漫游车、任务概念。

目录筛选“时代”与“类型”相互独立；一艘老飞船也可以继续运行，不能用年代自动判断任务状态。地区/机构作为资料与筛选字段，不做排名。

成熟度独立记录：
- L1：真实来源/明确重建的外观 + 旋转预览 + 伴飞/随船视角 + 稳定切换。
- L2：结构热点 + 少量经核实动作/材质精修 + 特定任务内容。
- L3：某个任务窗口的位置回放和可验证姿态。
- L4：单独验证的真实座舱、着陆、完整动力学。

首发以L1为基线，在2–3艘上做L2。未达标的条目可以在开发目录列出，不以“Coming soon”铺满孩子的默认机库。现实中的无人器具没有载人舱，不安排虚构L4驾驶舱。

### 3.1 原型三型

Apollo LM（多腿/分级结构）、Voyager（天线与长杆）、Webb A或B（大面积遮阳板/镜面）。三个外形差异很大的模型，足以暴露包围盒、材质、方向、相机、尺寸和切换问题。[V04][V06][V10][V11]

A/B不是已验证的一对LOD。先比较两个版本，选一个母本，再从同一母本生成低模。

### 3.2 首发目标：八种基础机型 + 一个未来项目

Apollo LM、Space Shuttle、Crew Dragon、Voyager系列、Cassini、Juno、Hubble、Webb。Voyager 1/2可有两个任务条目，但不为了凑数把同一外形算两套美术。[V04–V11][V22–V23]

内容目标为“8+1”：上述八种基础机型，再加至少一个明确标注的未来项目，优先Dragonfly。未来项目先做到L1即可，不要求首发全球地表飞行。九个目标不是九个已经就绪的资产；在V0/V2实测后确认完成顺序与发布范围，不能默默取消未来这一维度。

其中Crew Dragon是明确需求，必须在首发工作列表保留；本次只找到官方参考入口，未核实可复用的具体模型。按05文档走授权来源查找/独立外观重建路径，不以不存在的glb文件名交差。

### 3.3 未来与历史扩展

未来优先内容是Dragonfly：任务页面仍列为Future Mission；现有2026年8月模型包主要用于打印，必须独立加工。[V18][V19] 第一阶段允许在机库展示并进入明确标记的虚拟旅行；不因加入旋翼器就强制先做全球土卫六地形。真空中不播放旋翼推进教学。真正贴地飞行是单独地表样片。

ATLAST有轻量GLB，可作为“概念研究”展位；若Dragonfly暂未就绪，可以向用户明确提出先加入此概念展位，但不能无声替换Dragonfly，也不能写为当前获批准的发射任务。[V20] Europa Clipper已于2024年发射，不放到“尚未发射”列表。[V17]

历史拓展候选：Sputnik 1、Vostok、Mercury、Gemini、Apollo CSM、Soyuz、Shenzhou；其他探测主题包括中国探月/火星、日本小行星采样、ESA木星/彗星任务。这里是待研究队列，不是已验证资产清单。没有确认模型和授权的条目不假装已找到。NASA资产覆盖便利不能替代人类航天史的完整性。

火箭与航天器分开建模。Saturn V/Falcon/Starship整套发射系统如加入，应有“发射组合体/在轨飞船”构型；不让全套助推器永远飞在月球旁边。首发不要求完整发射过程。

## 4. 让不同载具有不同体验，不靠数值换皮

### 4.1 机库

每次只加载当前预览的3D模型，其余用本地生成的小缩略图。左右切换/分类可键盘和触控使用；转动/放大由用户控制，不空闲自动复位。

“便于查看”模式可以按屏幕占比自动构图；“真实尺寸比较”必须使用统一米制，附一把量尺。两者明示，不把各自填满卡片的效果当真实大小比较。

资料卡只默认显示：名字、类型、一个记忆点、过去/当代/研发/概念标签。尺寸、任务史、素材来源放展开层，不给孩子参数墙。

### 4.2 游戏中的视角

- 伴飞：船体真实3D出现在前景，占屏幕高度约15–25%作为初始可调目标；可绕船和看外部，不能永远强制尾追。
- 虚拟随船：在稳定虚拟观察点看向前方；不能飞进没有内壁的外部壳体。可显示简洁非真实仪表UI，但不标官方座舱。
- 自由观察天体：保留原来的天体绕看体验，可临时隐藏船；重新显示不更改天体和相对观察方位。
- 检查飞船：用户主动以飞船为观察对象；退出恢复之前视角。

真实座舱只对单独获得或制作并验收的内饰模型启用，外观GLB本身不证明存在座舱。

### 4.3 结构热点与动作

点天线/太阳能板/镜面/隔热层看一句短解释。首发优先静态热点；节点经核实、运动范围有依据后才增加展开、转动、舱门或分离。

不能假设glTF包含完整动画、骨骼或独立可动子件。不得把整网格围绕错误轴旋转来冒充真实机构。模型优化保留用于热点与铰链的语义节点；给它们分配稳定唯一ID，不只按容易重复的名称寻址。[V24–V27]

### 4.4 观察与照片

“游戏拍照”是虚拟相机截取当前渲染画面。“任务看见过什么”是来自档案的影像，显示目标、任务、日期、仪器/波段、处理方式和来源。两者分开。

Hubble/Webb观察模式可以以真实影像展示不同波段；不能在任意模型上套彩色滤镜后称为真实红外结果。Webb的真实任务位置/观察方向不能由自由旅行位置自动推导。[V13]

可选共同活动：给地球“发送一束信号”，按几何距离计算理论单程光行时间；显示动画加速与真实时长，明确忽略链路/处理/遮挡时不能叫真实通信仿真。[V28]

明信片保存vehicleId、variantId、destinationId、观察模式、日期、视角快照和图像来源标签。无需注册、联网、收集儿童资料。

## 5. 解耦不是只有一个vehicles文件夹

### 5.1 模块职责

| 模块 | 只负责 | 禁止做 |
|---|---|---|
| VehicleCatalog | 类型、资料、构型、素材版本、视角描述、可用能力 | 逐帧渲染、相机移动 |
| VehicleAssetAdapter | GLB导入、单位/轴/枢轴校正、材质与节点映射 | 写当前目的地/时间/相机 |
| AssetManager | 下载、解码、缓存、引用计数、失败状态、释放 | 偷偷选择刚加载好的模型 |
| VehicleInstance | 当前实例、局部姿态、可动件状态 | 自建全局动画循环、监听全局鼠标 |
| TravelController | 虚拟旅程路径、当前位置、打断与安全距离 | 因机型不同重写天体星历 |
| CameraController | 唯一主视角/相机状态写入者 | 接受贴图回调强制回正 |
| MissionRegistry | 条件、叙事、档案影像、可选历史轨迹适配 | 把每个探测器实现成一套游戏引擎 |
| ObservationProvider | 游戏截图/已归档科学影像/示意渲染的明确区分 | 以滤镜伪造测量 |
| HangarUI | 预览、筛选、换船命令 | 自行清空世界状态 |

这些可以是普通TS模块，不需要ECS、插件市场、后端服务、微前端或几十个空类。

### 5.2 三种身份必须分开

1. assetId：这份GLB及版本。
2. vehicleId / variantId：哪种飞船、哪种构型。
3. missionId：哪次历史任务/哪段阶段。

一个Voyager资产可以映射两个任务。一个Apollo任务需要多个构型。Crew Dragon对接型、穹顶型、不同cargo版本不能只换名字。[V04][V06][V22]

同样区分vehicle“产品定义”、玩家“实例”和真实任务“实例”。自由飞到土星的玩家Dragon，不能改写真实Dragon的历史轨迹。

### 5.3 推荐目录

```text
src/
  core/{Simulation,TravelController,CameraController}.ts
  vehicles/{VehicleCatalog,VehicleInstance,VehicleAssetAdapter}.ts
  assets/AssetManager.ts
  missions/{MissionRegistry,ObservationProvider}.ts
  ui/{Hangar,VehicleBadge,VehicleDetails}.tsx
public/
  vehicles/<asset-id>/<version>/{vehicle.glb,preview.webp,vehicle.json,NOTICE.txt}
  mission-content/<pack-id>/...
assets-source/     # 原文件与许可快照；不直接打进网页
scripts/          # 可重现转换、校验、预览和清单构建
```

文件名只是建议；已有工程就增量适配，不能按此树全量重写。contracts/vehicles.ts提供独立类型示例，不代表已接入旧工程。

## 6. 数米飞船与天文距离如何同屏

### 6.1 数据空间先统一

天体/旅程锚点：双精度公里，明确参考系。航天器模型：米，右手坐标、+Y上、+Z资产正面。[V25] 相机可以在自己系统中沿-Z看，但导入器必须明确变换，不把摄像机方向约定当模型的默认轴。

先从CPU双精度位置中减去当前相机/局部原点，再提交GPU；模型每个顶点不得直接加上数十亿公里的位置。禁止为了可见而把飞船实体变成几千公里大。

### 6.2 推荐可落地的近/远场方案

由同一个CameraController输出统一ViewSnapshot：惯性空间相机位置、朝向、FOV、aspect及模式。场景渲染器根据这个快照构建两个只读渲染视图，不运行两个相互争抢的控制器。

远场：天体位置为 `(bodyPositionKm - cameraPositionKm) / farUnitKm`，天体半径同除farUnitKm；远场相机在原点。
近场：载具位置为 `1000 * (vehicleAnchorKm - cameraPositionKm)` 再叠加模型局部米制变换；近场相机也在原点；两者共享朝向、FOV、aspect。航天器不是纯HUD贴片，可以绕看、有相对运动和光照。

两个pass可在同一个WebGLRenderer中完成。先绘远场，再在满足分离条件时清除深度绘近场。**这不是通用正确的遮挡方案**：它仅适用于所有天体/环表面都远于全部近场几何，且旅行保持安全距离的场景。必须在运行时验证这个分离约束，不能无条件clearDepth让船永远盖住星球。

首版控制近场范围（例：0.05–1000米，具体按机型调），确保所有远场可见表面远大于该范围；碰撞/安全检测包括相机、船体包围体、星环范围而不只行星中心。到达安全边界停止接近，不能穿进球体。未来要贴地、穿环、近距离对接其他远场物体，再实现统一局部深度/正确跨pass深度合成，不在首版偷偷突破前提。

对于太阳系导航全景，仍用原方案的压缩距离和图标，不把真实船体在全景中强行放大。进入局部/近景才展示可辨识的船。

### 6.3 航行和姿态

旅行时的游戏锚点与机型无关。切船不改出发点/终点、不重算行星位置、不按所谓最高时速重写秒级旅行。现实中的位置、速度方向、姿态、仪器视轴是四件事；首发姿态是明确的舒适虚拟姿态，实际复现另接数据。

不让所有飞船持续喷出同一种飞机尾焰。教学/物理表现按构型只在相应机动展示短效果；自由旅行的过渡特效要标为虚拟。不要通过模拟真实自旋让随船视角强制滚转、眩晕。

## 7. 换船是事务，不是把旧模型删了再等网络

状态分离：activeVehicle、previewVehicle、pendingSelection、travelState、cameraView、missionMode。机库预览不自动装备。

每次点击“使用”分配递增requestId/commandId：
1. 原载具和世界继续可用，显示新载具加载状态。
2. AssetManager请求资源；可复用已有只读几何/纹理但实例动作状态独立。
3. 解码、校验、建立锚点、准备材质，仍不动镜头。
4. 等待过程中再次换船，旧请求即使不可取消解码，也失去提交权限。
5. 只有仍是最新请求且准备成功，才原子交换active实例；保持旅程锚点、目标、时间、相机方位。
6. 交换后释放旧实例引用；不能释放仍被机库或其他实例共享的资源。
7. 失败保留原船、保留当前视角，给重试；不退回地球、清空画面、默默换占位模型。

大小差异导致当前视角不适合时：随船前视应保留世界相机；伴飞可保持世界相机后重新求新船的相对构图偏移，只改变明确的展示偏移，不改变真实旅程锚点；或主动提示“适配新船视角”。不能暗中改变用户绕天体的方位。只有用户同意fit时才平滑调整距离。

“飞往这里”和“换船”使用不同的命令令牌，换船不能无意取消/重启飞行；新目的地命令照常取消旧旅程。UI关闭/组件卸载不得dispose整个共享renderer。

## 8. 资源格式、材质与预算

优先glTF2/GLB；Three.js有直接加载路径，包含动画时也可读；使用压缩扩展必须配置对应decoder。[V24] NASA新目录有多种格式，GLB资产和打印STL要分开。[V01]

源模型低细节并不意味着不可用，但不能把“NASA来源”当作电影质量保证。本次查看Apollo LM和Webb A的官方预览：外形可辨认，材质呈简化效果。下一步应先提高正确光照、材质粗糙度/金属度和有限纹理，而不是立即购买超高面数模型。

外观材质通常是一组部件材质与可能的UV纹理，不是像星球一样一张长方形展开图就够。需要逐件检查baseColor、normal、metallic/roughness、AO、emissive、UV和外部文件。高反射金属需要合理环境反射；远离太阳的飞船可以有明确可关闭的教学补光，不用全unlit掩盖材质问题。

建议初始预算（未实测）：当前一艘active高精模型 + 至多一艘pending/preview；常规船体20k–100k三角形、尽量低于150k；低档5k–25k；每艘约5–20个材质/绘制批次为努力目标；纹理1K/2K优先，单个载具约32–64MiB GPU纹理预算起点，必须计入原项目总预算，不能额外无上限叠加。

交付GLB尽量1–6MB，超过8–10MB进入人工复核而不是一刀切失败；原始Clipper为34.05MB是页面下载体积，不等于GPU占用或必定超面数。[V16] 纹理解码/着色器编译时间也计入切换延迟。几何压缩不等于把纹理显存同步压小。

先无压缩正确导入3艘，再依据inspect结果有选择地做减面、合批、WebP或KTX2、Meshopt/Draco。不要无脑flatten/join，破坏热点、镜面、遮阳板、太阳翼、舱门和分离层级。A/B来源不同模型不能直接当LOD来回闪变。[V26]

异步释放注意材质、纹理、geometry、AnimationMixer引用、object URLs、解码worker和预览render target；renderer.info只用于资源数量/绘制统计，不宣称精确VRAM。连续切换与机库开关需有稳定的缓存上限。

## 9. 资产从网页走向生产的门禁

source page verified → downloaded → legal-reviewed → structurally-validated → visually-approved → integrated/performance-tested → published。

必须保存：来源页、原始文件/日期/SHA-256、创作者、逐件许可、是否允许随网页交付可下载模型、构型、模型版本、单位/轴/比例变换、纹理依赖、简化和修改记录、最终文件SHA-256、预览、真实运行统计、注意事项。

NASA总体允许很多教育/信息用途，但含第三方作品与品牌标识的素材仍按具体条件处理；不能用本项目标志暗示NASA/SpaceX/ESA背书。[V03] 代码开源许可与模型/照片/音频许可分开记录。网页GLB对用户可取得：标为仅渲染成图、仅编辑用途或禁止分发源素材的资产，不自动适用于这个网页游戏。

ESA影像一般条件与特定CC许可不同，而且影像条件不能直接当3D模型许可。[V30] 本包不给全部素材笼统贴CC0或MIT。

AI做代码、转换脚本、UV修复、LOD、材质辅助合适；把一张照片生成想象背面然后标“真实CAD”不合适。独立重建可以用，但必须标“基于公开参考的外观重建”，参考图的使用与商标等仍须检查。不要给AI生成图加机构标志并暗示官方。[V03]

## 10. 分期实施与交接

V0：机库试验台和3艘资产核验，6–10h。
V1：通用实例/切换/状态隔离，14–24h。
V2：实际世界的伴飞、随船、尺度与旅行集成，12–22h。
V3：扩充八种基础机型、两个轻任务内容包、明信片字段，18–32h；未来项目优先Dragonfly另做资产样本核验和加工估算，纳入“8+1”内容目标。
V4：性能、触控、失败恢复、回归与备份，10–18h。

在素材可取得且只需常规清理的假设下，约60–110有效小时；加25%缓冲约75–140h。不是模型运行时间，不是交付保证，也不含全部座舱/高精真实飞控。与原工程模块存在重叠，不把原计划和本计划无脑相加；V2完成用实际耗时重估。

Crew Dragon模型许可未核实，可能新增独立外观制作/授权沟通工作，不隐含在“八个现成模型”里。Dragonfly打印转网页或重建也单独估算，先做2–4h样本检查再决定继续减面或重建；未知工时不靠不负责任的小数字填平。

V0不是必须让整个地月主工程等待。可以在同一代码库的独立开发路由/测试场景并行开展，但只一个主写作者，资产整理和只读审查可由第二Agent做。V2把已经验证的模块接入M1/M2；不等17天体全做完才补载具。
